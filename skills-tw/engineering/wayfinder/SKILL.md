一個鬆散的構想出現了，大到單一 agent session 裝不下，而且籠罩在迷霧中：從這裡到**目的地**的路徑還看不見。尋路（Wayfinding）講的是找出那條路，而不是直衝目的地。這項技能會在儲存庫的議題追蹤器上，將路徑繪製成一份**共享地圖**，然後逐一處理其中的**決策工單**（這些問題的解答是一項決策，而不是可執行的建置切片），直到路線清晰為止。

目的地依每項工作而異，替它命名是繪製地圖的第一個動作：它會形塑每一張工單。它可能是一份要交接並持續迭代的規格、一項在規劃開始前要鎖定的決策，或是一項就地完成的變更，像是資料結構遷移。這份地圖與領域無關：工程工作、課程內容，任何符合這個形狀的工作都適用。

## 只規劃，不動手

Wayfinder 預設是**規劃**：每張工單解決一項決策，而地圖完成的定義是路徑已清晰，在有人動手去做這件事之前已經沒有東西要決策了。想直接動手做工作的衝動，通常就是你已經抵達地圖邊緣、該交接出去的訊號。一項工作可以在其**Notes**中覆寫這個原則，把執行也納入地圖本身，但若沒有這樣說明，就只產出決策，而非交付物。

## 以名稱指稱

每一份地圖與工單都是一個議題（issue），因此都有一個**名稱**：它的標題。在人類會閱讀的一切內容中（敘述、地圖的「Decisions so far」），都以該名稱指稱它，絕不使用單純的 id、編號或 slug。一整排的 `#42, #43, #44` 讓人看不懂；名稱則能一眼讀懂。id 與網址並不會因此消失；名稱會把連結包在裡面，但它們只存在於名稱**內部**，絕不能取代名稱本身。

## 地圖

地圖是這個儲存庫議題追蹤器上的單一議題，標記為 `wayfinder:map`，是規範性的產物（canonical artifact）。它的工單是這份地圖的子議題（child issues）。

地圖是一份**索引**，不是儲存庫。它列出已做出的決策，並指向存放細節的工單；一項決策只存在於一個地方，也就是它的工單，所以地圖絕不重述決策內容，只做摘要並附上連結。

**地圖、其子工單、阻擋關係（blocking）與前緣查詢實際存放在哪裡，取決於所使用的追蹤器。** 議題追蹤器應該已經提供給你了。若沒有，請告訴使用者執行 `/setup-matt-pocock-skills`。請查閱追蹤器文件中的「Wayfinding operations」章節，了解*這個*儲存庫如何表達這些概念。若沒有提供任何追蹤器，則預設使用 local-markdown 追蹤器。

### 地圖本文

整份地圖以低解析度呈現，每個 session 只載入一次。未結案的工單**不會**列在這裡：它們是開放的子議題，透過查詢找到。

```markdown
## Destination

<抵達這份地圖終點會是什麼樣子：這項工作正在尋找通往的規格、決策或變更。一到兩行；每個 session 在選擇工單之前都要先對齊這個方向。>

## Notes

<領域；每個 session 都應該查閱的技能；這項工作的既定偏好>

## Decisions so far

<!-- 索引：每張已結案工單一行，足以判斷相關性，然後點進連結查看工單所存放的細節 -->

- [<已結案工單標題>](link): <一行摘要答案>

## Not yet specified

<!-- 見「Fog of war」：範圍內但尚無法開票的迷霧，會隨著前緣推進而升級 -->

## Out of scope

<!-- 見「Out of scope」：被判定超出目的地範圍的工作；已結案，永不升級 -->
```

### 工單

每張工單都是地圖的**子議題**；追蹤器的議題 id 就是它的身分。它的內文是問題本身，大小設計為一個 100K token 的 agent session 可以處理：

```markdown
## Question

<這張工單要解決的決策或調查>
```

每張工單都帶有一個 `wayfinder:<type>` 標籤，為 `research`、`prototype`、`grilling`、`task` 之一(見[Ticket Types](#ticket-types))。

一個 session 透過將工單指派給推動這份地圖的開發者來**認領**工單，而且要**先**做這件事，任何工作開始之前，這樣同時進行的其他 session 才會跳過它。那個指派對象*就是*認領的證明：一張開放且未指派的工單就是未被認領。

阻擋關係使用追蹤器**原生**的相依關係：這點很重要，因為它能在追蹤器自身的 UI 中*視覺化*呈現前緣，讓人類不用打開地圖就能看到哪些工單可以動手做。只有在追蹤器缺乏原生阻擋功能時，才退而使用內文慣例來表示。當阻擋某張工單的所有工單都已結案時，該工單就是**未被阻擋**的；**前緣（frontier）**指的是開放、未被阻擋、未被認領的子工單，也就是已知範圍的邊界。

答案不屬於工單內文的一部分；它是在解決時才被記錄下來的(見[Work through the map](#work-through-the-map))。解決工單過程中建立的資產（assets）應以連結方式附加在議題上，而不是貼在內文裡。

## Ticket Types

每張工單不是**HITL**（human in the loop，與能代表自己發言的人類一起完成的工作），就是**AFK**，由 agent 獨立驅動。HITL 工單只能透過那場真實的互動來解決；agent 絕不能代替人類那一方發言（一個自問自答的 grilling agent 就是違反了這一點）。

- **Research**（AFK）：閱讀文件、第三方 API，或本地資源如知識庫，以找出某項決策正在等待的事實。由一個子代理（subagent）呼叫 Skill 工具、使用「research」來解決。當需要目前工作目錄之外的知識時使用。
- **Prototype**（HITL）：透過呼叫 Skill 工具使用「prototype」，製作一個便宜、粗糙、具體的產物（大綱、粗略草案、雛型，或 UI/邏輯程式碼）供人反應，以拉高討論的精細度。將原型以資產形式連結。當關鍵問題是「它應該長什麼樣子」或「它應該表現得如何」時使用。
- **Grilling**（HITL）：對話。預設情況。一律呼叫兩次 Skill 工具，分別用於「grilling」和「domain-modeling」。
- **Task**（HITL 或 AFK）：在能做出*決策*之前必須完成的人工作業：沒有東西要決策、雛型化或研究，但討論會被卡住，直到這件事完成。例如註冊某項服務以便判斷其 API、申請存取權限、搬移資料以便看清其形狀。這是唯一一種*做*而非*決策*的工單類型，它之所以有存在的意義，是因為它能解除某項決策的阻擋，而不是因為它交付了目的地本身。agent 能自己驅動的部分就自己做（AFK）；否則就交給人類一份精確的檢查清單（HITL）。當工作完成時就算解決；答案會記錄做了什麼，以及後續工單所依賴的任何結果事實（憑證存放位置、新的網址、資料筆數）。

## Fog of war

地圖*刻意*不完整：還看不見的東西就不要畫上去。在現有工單之外，是**戰爭迷霧（fog of war）**：那些你能感覺到即將出現、但還無法明確定案的決策與調查，因為它們仰賴目前仍未解決的問題。解決一張工單會清除它前方的迷霧，把現在可以明確化的部分逐一升級成新的工單，直到通往目的地的路徑清晰、不再有任何工單為止。

地圖的**Not yet specified**區塊就是記錄這種模糊視野的地方：被懷疑存在的問題、日後要重新檢視的領域。它是通往目的地路上尚未被發現的前緣：這裡的一切都在範圍之內，只是還不夠明確，無法開票。可以寫得盡量鬆散或盡量詳盡，視你目前能看到多清楚而定；它同時也作為路標，讓協作者了解這項工作正朝哪裡前進。

**該歸入迷霧，還是開票？** 判斷標準在於你現在能不能精確地陳述這個問題，而*不是*你現在能不能回答它。

- **當**問題已經明確，即使目前被阻擋、你還無法動手，也**該開票**。
- **當**你還無法把問題講得那麼精確時，**該歸入 Not yet specified**。不要把迷霧預先切成工單大小的碎片：它比一張工單還要粗略，而且一塊迷霧一旦被前緣推進到，可能升級成好幾張工單，也可能一張都沒有。

**Not yet specified** 不包含已經決定的事項（Decisions so far）、已經是現有工單的事項，以及超出範圍的事項（下一節）。

## Out of scope

迷霧只會朝*目的地*的方向聚集。目的地決定了範圍，因此超出目的地之外的工作屬於**超出範圍（out of scope）**：它不是迷霧，也不屬於**Not yet specified**。它會有自己專屬的**Out of scope**區塊：記錄你有意識地排除在*這項*工作範圍之外的內容。決定它歸屬於此的是範圍，而不是明確程度。

超出範圍的工作永遠不會升級（前緣止步於目的地），所以它只有在目的地被重新劃定時才會回歸，而且屆時是作為一項全新的工作，而不是延續原本的工作。

判定某件事超出範圍是一個劃定範圍的動作，而不是路線上的一步。當一張既有的工單後來發現其實落在目的地之外（可能是繪製地圖時範圍劃錯，或是某次解決工單時才暴露出來），就**把它結案**（已結案的工單能明確地不再屬於前緣），並在**Out of scope**區塊留下一行紀錄：摘要加上為何超出範圍的原因，並連結該已結案工單。它不會出現在**Decisions so far**中，因為那裡記錄的是實際走過的路線；劃定範圍的邊界不算路線上的一步。

## Invocation

有兩種模式。無論哪一種，**每個 session 絕不解決超過一張工單**，研究類工單除外。

### 繪製地圖

使用者以一個鬆散的構想來呼叫。

1. **為目的地命名。** 呼叫兩次 Skill 工具，分別用於「grilling」和「domain-modeling」，以確立這份地圖要找的路通往何處：規格、決策或變更。目的地決定了範圍，所以要最先確立下來。
2. **繪製前緣。** 再次進行 grilling，這次採取**廣度優先**：在整個空間中橫向展開，而不是深挖任何一條思路，浮現出待決的問題以及現在就能踏出的第一步。**若這一步沒有浮現任何迷霧**（通往目的地的路已經清晰，整趟旅程小到一個 session 就能完成），那你就不需要地圖。停下來，詢問使用者希望如何進行。
3. **建立地圖**(標記 `wayfinder:map`)：填好 Destination 和 Notes,Decisions-so-far 留空，把迷霧勾勒進**Not yet specified**。
4. **建立現在就能明確定義的工單**，作為地圖的子議題，然後在**第二輪**佈線阻擋關係邊（議題要先有 id 才能互相參照）。佈線會把工單分類到前緣與被阻擋兩類；所有還無法明確定義的部分則留在迷霧中，也就是**Not yet specified**區塊。
5. **啟動研究子代理。** 針對剛建立的每一張 `research` 工單，啟動一個子代理呼叫 Skill 工具使用「research」，平行解決它，並將發現內容記錄在一個用完即丟的 `research/<name>` 分支上，並在工單上留下一個指向該內容的指標。
6. 停止：繪製地圖是單一 session 的工作；它不會親手解決任何工單。

### 處理地圖中的工單

使用者以一份地圖（網址或編號）來呼叫。指定一張工單是**可選的**：若沒有指定，則由你自己選出下一項決策，而不是讓使用者選。

1. 載入**地圖**：低解析度的視圖，而不是每張工單的完整內文。
2. 選擇工單。若使用者指定了某張工單，就用那一張。否則依順序取前緣中的第一張工單。**認領它**：在動手做任何工作之前先指派給自己。
3. 解決它。**依需求放大細節**：視需要即時取得任何相關或已結案工單的完整內文；呼叫 `## Notes` 區塊中提到的任何技能所對應的 Skill 工具。若有疑慮，就呼叫兩次 Skill 工具，分別用於「grilling」和「domain-modeling」。
4. 記錄解決結果：將答案以**結案留言（resolution comment）**發布、**結案**該議題，並在地圖的 Decisions so far 中**附加一個指標**。
5. 加入新浮現的工單（先建立再佈線）；將答案已使其可明確化的迷霧升級成工單，並把每個已升級的部分從**Not yet specified**中清除，讓它只以新工單的形式存在。若答案顯示某張工單（不論是這張或其他張）其實落在目的地之外，就**將其判定為超出範圍**，而不是在路線上把它解決掉。若這項決策使地圖的其他部分失效，就更新或刪除那些工單。

使用者可能會平行處理多張未被阻擋的工單，所以要預期會有其他 session 同時在編輯這個追蹤器。
