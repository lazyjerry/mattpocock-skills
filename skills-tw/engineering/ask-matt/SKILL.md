# Ask Matt

你不可能記得每一個技能，所以就直接問吧。

一個 **flow（流程）** 是穿越各技能的一條路徑。大多數路徑都沿著一條**主流程**行進，並有兩個**匝道**匯入其中。其餘的則是獨立技能，或是在底層運作的詞彙層。

## 主流程：從想法到出貨

大多數工作行經的路線。你有一個想法，想把它做出來。

1. **`/grill-with-docs`** 透過訪談來打磨想法。只要你**在某個工作目錄中作業**，就從這裡開始：它是有狀態的，會把學到的內容保留在 `CONTEXT.md` 與 ADR 中。（沒有工作目錄？改用 `/grill-me`，詳見「獨立技能」段落。兩者都執行同一個 `/grilling` 原語；`grill-with-docs` 是會留下書面紀錄的那一個，所以只要有儲存庫可以留紀錄，它就是兩者中較好的選擇。）
2. **分支：你能在對話中把每個問題都解決嗎？** 如果有個問題需要一個可執行的答案（狀態、商業邏輯，或是你必須親眼看到的 UI），就繞道經過一個原型，並透過 **`/handoff`** 雙向銜接（原型有自己的目錄，這正是 `/handoff` 的用途；參見「階段邊界」）:
   - **`/handoff`** 出去，然後對著那個檔案開啟一個新的 session,
   - **`/prototype`** 用可拋棄的程式碼來回答問題，
   - **`/handoff`** 把學到的東西帶回來，並從原本的想法討論串中參照它。
3. **分支：這是一個多 session 的建置嗎？**
   - **是** → **`/to-spec`**（把討論串轉成一份規格書），接著用 **`/to-tickets`** 把它拆成一批 tracer-bullet 工單，每張工單都宣告自己的**阻擋關係（blocking edges）**。在本地追蹤系統中，這是 `.scratch/<feature>/issues/` 底下每張工單一個檔案，依阻擋關係手動由前往後處理；在真正的追蹤系統中，這些關係會變成原生的阻擋連結，因此任何阻擋者都已完成的工單即可被領走：對每張工單啟動 **`/implement`**，每完成一張就 **`/clear` 清空 context**。每張工單都是自成一體的，所以最後一張的 context 可以直接丟棄。
   - **否** → 直接在同一個 context window 中執行 **`/implement`**。

   無論哪種情況，**`/implement`** 都會在內部驅動 **`/tdd`** 來建置每個 issue（一次一段紅燈變綠燈的切片），最後在提交（commit）前執行 **`/code-review`**，對這份 diff 做雙軸審查（標準 + 規格）來收尾。當你只是想不靠完整規格、以測試先行的方式打造一個具體行為時，單獨使用 **`/tdd`**；當你只是想針對某個固定基準點審查一個分支或 PR 時，單獨使用 **`/code-review`**。

### Context 衛生

把步驟 1 到 3 保持在**同一個不中斷的 context window** 中（在 `/to-tickets` 之前不要 compact 或 clear），讓打磨想法、撰寫規格、拆分工單都建立在同一套思考脈絡上。之後每次 **`/implement`** 都會重新開始，從工單本身出發。

這麼做的限制在於 **[smart zone](https://www.aihero.dev/ai-coding-dictionary/smart-zone)**：也就是模型仍能保持敏銳推理的那個範圍（在最先進的模型上大約是 15 萬個 token）。如果一個 session 在 `/to-tickets` 之前就快逼近這個上限，不要在品質下降的狀態下硬撐；在最近的階段邊界執行 `/compact`，然後繼續進行（參見「階段邊界」）。

## 匝道（On-ramps）

一個會產生工作項目、之後匯入主流程的起始情境。

- **Bug 與需求堆積如山** → **`/triage`**。它會讓 issue 經過分流角色的處理，產出可直接交給 agent 執行的 issue，之後由 **`/implement`** 接手。

  Triage 只適用於**不是你自己建立**的 issue：錯誤回報、外部提出的功能需求，任何原始送進來的東西。`/to-tickets` 產出的工單已經是可直接交給 agent 執行的了，所以**不要對它們做 triage**。

- **有東西壞了** → **`/diagnosing-bugs`**。適用於難搞的情況：第一眼看不出所以然的 bug、間歇性的閃現故障、在兩個已知正常的狀態之間悄悄潛入的迴歸問題。它拒絕在還沒建立**緊密的回饋迴圈**（有一個指令已經能在*這個* bug 上重現紅燈）之前就開始理論化，然後用一個回歸測試來修復。它的事後檢討（post-mortem）會在真正的發現是「沒有好的切入點可以把這個 bug 鎖住」時，轉交給 **`/improve-codebase-architecture`**。

- **一個龐大、模糊的工程：一個全新專案或一個巨大的功能建置，大到一個 session 裝不下** → **`/wayfinder`**，這裡認知負荷最重的流程。當從這裡到目的地的路徑還看不見時，它會繪製一張**共享地圖**，由**決策工單（decision tickets）**組成、放在 issue 追蹤系統上，並逐一解決，產出的是**決策，而非交付物**，直到迷霧散去、道路清晰。**`/grill-with-docs`** 打磨的是你一次 session 就能裝下的想法，wayfinder 則是給你裝不下的想法用的，它比較慢也比較密集，所以要留給正好符合這種情況的場合，絕不要用在範圍界定清楚的功能上。

  當地圖清晰之後，**它負責交接，不負責建置**：在 **`/to-spec`** 匯入主流程，把地圖上相連的決策收斂成一份可建置的計畫，然後照常走 `/to-tickets` 與 `/implement`。如果把地圖直接丟進 `/implement`，就會跳過那個收斂步驟，並丟掉相連的細節，所以只有在這件事其實規模不大時，才直接走 `/implement`。

## 程式碼庫健康度

不是功能開發，只是維護保養。

- **`/improve-codebase-architecture`** 在你有空檔時執行，用來讓程式碼庫維持在適合 agent 操作的良好狀態。它會找出**可深化的機會**；挑選其中一個會_產生一個想法_，你可以帶著它在 `/grill-with-docs` 進入主流程。它是負責找出候選項目的調查工作；下方的 **`/codebase-design`** 則是你設計已選定項目的工作台。

## 底層詞彙

兩個由模型自行呼叫的參考資料，運作在其他技能*之下*，各自是其詞彙的唯一真實來源。當問題出在**用詞**本身而非流程時，直接使用它們；或讓上面那些技能自行引用它們。

- **`/domain-modeling`**：打磨專案的*領域（domain）*語言：挑戰一個模糊的詞、解決一個被過度使用的詞（例如「account」同時做三件事）、把一個難以回頭的決策記錄成 ADR。這是 `/grill-with-docs` 用來維持 `CONTEXT.md` 是一份乾淨詞彙表的積極訓練。
- **`/codebase-design`** 是設計模組*形狀*的深層模組詞彙（module、interface、depth、seam、adapter、leverage、locality）：在乾淨的介接點（seam）之後，用小小的介面（interface）承載大量行為。`/tdd` 與 `/improve-codebase-architecture` 都會用到這套詞彙。

## 階段邊界

一個**階段（phase）**是 session 內的一個工作區塊：打磨想法、實作、QA。在兩個階段之間的**邊界**上，你有五個選項，而在它們之間做選擇是這整張地圖裡最模糊的決策：

- **繼續（Continue）**：原地不動。不花任何成本，也不會失去任何東西。
- **`/clear`**：清空 context window，適用於這裡的一切都與接下來無關的時候。
- **`/handoff`** 寫出一份可攜帶的 markdown 檔案。用途很窄：只適用於**新的執行環境（harness）**、**新的目錄**、**一位同事**，或是在**階段進行中**分岔出一個支線任務。它換來的是可攜性。
- **子代理（Subagent）**：把一項範圍明確的任務送到它自己的 window 中，再取回一份報告。
- **`/compact`** 壓縮目前的 context，並用它來播種一個新的 session。這是**預設選項**，位於決策樹的最底層，而不是第一個該伸手去拿的選項。

閱讀 [PHASE-BOUNDARIES.md](PHASE-BOUNDARIES.md) 以取得完整的決策樹：五個問題、每個分支背後的理由，以及為什麼「主要來源成本」讓「繼續」成為第一個該排除的選項。要**在**邊界上做這個決策；在階段進行中，就繼續或是把剩下的工作拆給子代理。

## 獨立技能

完全不在主流程上。

- **`/grill-me`**：與 `/grill-with-docs` 一樣是不留情面的訪談，但是**無狀態的**：它不會在本地儲存任何東西，也不會建立 `CONTEXT.md`。當你**不在工作目錄中**時使用它（打磨一個計畫、一個設計、一篇文章，任何底下沒有儲存庫的東西）。如果你身在工作目錄中，改用 `/grill-with-docs`：它執行同一套訪談，還會留下書面紀錄，所以它絕對是兩者中較好的選擇。
- **`/grilling`** 是訪談本身的原語：回合、前緣（frontier），事實是 agent 的工作，決策則是你的工作。`/grill-me` 與 `/grill-with-docs` 是進入它的兩個具名途徑；`/triage`、`/wayfinder` 與 `/improve-codebase-architecture` 內部都會執行它。只有在你想要不加任何包裝、直接進行訪談時，才直接使用它。
- **`/resolving-merge-conflicts`** 逐個 hunk 處理進行中的 merge 或 rebase 衝突，依照追溯到雙方主要來源的**意圖**來解決，而不是靠挑選行號來解決，然後完成該操作。它絕不會執行 `--abort`。獨立技能，不在任何流程上：當你已經處於衝突當中時使用它。
- **`/prototype`** 是一個小型、可拋棄的程式，用來回答一個設計問題：這個狀態模型感覺對不對，或是這個 UI 應該長怎樣。「可拋棄」是對程式碼寫法的一種約束，而不是一定要銷毀它的承諾：答案會被收納進真正的程式碼中，而原型本身會被保留下來，作為 main 分支之外 `prototype/<name>` 分支上的一份**主要來源**，並從實作 issue 中指向它。它是主流程第 2 步中的繞道，但只要有一個設計問題難以在紙上定案，任何時候都可以使用它。
- **`/research`**：把閱讀的苦力工作委派給一個**背景 agent**：它針對一個問題調查**主要來源**，然後在儲存庫中留下一份附引用的 Markdown 檔案。你可以在它閱讀的同時繼續工作。它產出的檔案是可以帶*入*主流程、在 `/grill-with-docs` 使用的東西，因為研究是餵給思考用的，而不是取代思考。
- **`/to-questionnaire`** 適用於卡住你的東西不在你腦中、也不在程式碼庫中，而是在**別人腦中**的時候，它會幫你寫一份問卷讓對方填寫。它是 `/grill-me` 的反向操作：不是就主題訪問你，而是就**發送**這件事訪問你（要寄給誰、你需要拿回什麼），並把問題對準那個缺口。回收來的內容可以做為 `/grill-with-docs` 或 `/to-spec` 的素材。
- **`/wizard`** 適用於只有**人類**才能執行的步驟：佈建基礎設施、設定憑證或 CI 密鑰、在不熟悉的第三方儀表板中點選操作、執行一次性的 migration 或 cutover。它會產生一個互動式的 bash 腳本，依序開啟每個 URL、擷取每個值，並寫入 `.env` 與 GitHub secrets，讓這個流程不再需要每次都重新跟 agent 解釋一遍。由模型自行呼叫，所以 agent 一碰到只有人類能跨越的關卡就會立刻使用它。如果 agent 自己就能做到，那就應該自己做；這個技能是給人類真正需要親自介入的情況用的。
- **`/wait-what`** 是給一則沒有傳達到位的訊息用的修正措施。在對話中途使用，或是在任何其他技能內部使用，agent 會用你原本欠缺的脈絡，以白話文、搭配 `CONTEXT.md` 的詞彙，重新說明它剛剛講的內容。它是事後補救；`/grill-with-docs` 才是事前的解方，因為及早建立的共通語言，正是阻止術語從一開始就冒出來的做法。
- **`/teach`**：跨多個 session 學習一個概念，把目前的目錄當作一個有狀態的工作空間。
- **`/writing-for-agents`** 是撰寫給 agent 消費的文件（技能、AGENTS.md、被指向的文件）的參考資料。

## 前置條件

**`/setup-matt-pocock-skills`**：在你進行第一個工程流程之前先執行，用來設定其他技能所假設的 issue 追蹤系統、triage 標籤與文件配置。自訂的 issue 追蹤系統也適用。
