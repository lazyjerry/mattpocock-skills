這個 skill 會取用目前的對話脈絡與對程式碼庫的理解，產出一份規格文件。請勿詢問使用者，只要統整你已經知道的內容即可。

議題追蹤系統與分流標籤詞彙表應該已經提供給你了。如果沒有，請告訴使用者執行 `/setup-matt-pocock-skills`。

## 流程

1. 探索程式碼庫，了解目前的程式碼狀態（如果你還沒做過的話）。整份規格文件中請使用專案的領域術語詞彙，並遵循你所處理範圍內的任何 ADR。

2. 找出你要在哪些接縫（seam）測試這項功能。應優先使用既有的接縫。盡量選用最高層級的接縫。如果需要新的接縫，請在盡可能高的層級提出。程式碼庫中跨越的接縫越少越好，理想數量是一個。

跟使用者確認這些接縫是否符合他們的預期。

3. 依照以下範本撰寫規格文件，然後發布到專案的議題追蹤系統。套用 `ready-for-agent` 分流標籤，不需要額外分流。

<spec-template>

## Problem Statement

從使用者的角度描述他們所面臨的問題。

## Solution

從使用者的角度描述這個問題的解決方案。

## User Stories

一份很長、有編號的使用者故事清單。每則使用者故事應採用以下格式：

1. 身為 <actor>，我想要 <feature>，以便 <benefit>

<user-story-example>
1. 身為行動銀行客戶，我想查看帳戶餘額，以便更充分掌握支出決策所需資訊
</user-story-example>

這份使用者故事清單應該非常詳盡，涵蓋這項功能的所有層面。

## Implementation Decisions

列出所做的實作決策，可以包含：

- 將建置／修改的模組
- 這些模組將被修改的介面
- 開發者提供的技術澄清
- 架構決策
- 資料庫結構（schema）變更
- API 合約
- 特定的互動方式

請勿包含具體的檔案路徑或程式碼片段，因為它們很快就可能過時。

例外情況：如果原型（prototype）產出的程式碼片段能比文字敘述更精確地表達某項決策（例如狀態機、reducer、schema、型別結構），可以將其內嵌在相關決策中，並簡短註明這是來自原型。只保留能表達決策重點的部分，而不是完整的展示程式碼，只要重要的部分即可。

## Testing Decisions

列出所做的測試決策，需包含：

- 說明什麼樣的測試才算是好的測試（只測試外部行為，不測試實作細節）
- 哪些模組將會被測試
- 程式碼庫中類似測試的先例（prior art）

## Out of Scope

描述這份規格文件中不包含的範圍。

## Further Notes

關於這項功能的其他備註。

</spec-template>
