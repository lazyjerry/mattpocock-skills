# 邏輯原型（Logic Prototype）

一個單一、獨立的 HTML 檔案（**可分享的展示**），讓任何人都能透過點擊按鈕來操作狀態模型。當問題與**商業邏輯、狀態轉換或資料結構**有關時使用：那種在紙上看起來合理，但只有實際套用真實案例才會發現不對勁的東西。

因為它是一個不需要安裝任何東西的單一檔案，你可以把它交給非開發人員（設計師、PM、領域專家），讓他們親自感受這個模型。所以它說的是他們的語言，而不是程式碼的語言。

## 適合使用這個形式的情況

- 「我不確定這個狀態機是否能處理先 X 後 Y 的邊界情況。」
- 「這個資料模型是否真的能表示……的情況」
- 「我想在寫程式之前先試探一下 API 應該長什麼樣子。」
- 任何想要**按按鈕、觀察狀態變化**的情況。

如果問題是「這東西應該長什麼樣子」，那這個分支就不對了。請改用 [UI.md](UI.md)。

## 流程

### 1. 陳述問題

在寫程式碼之前，先寫下你正在原型化的是什麼狀態模型、要回答什麼問題。用一段文字寫在展示的最上方（放在明顯的簡介中，而不只是註解裡）。一個回答錯誤問題的邏輯原型純粹是浪費，所以要把問題寫清楚，以便之後可以檢查，不論使用者現在正在看，還是之後才回來查看。

### 2. 將邏輯獨立成可攜的模組

把實際的邏輯（用來回答問題的那部分）放在單一個 `<script>` 區塊裡，寫成一個小型、純粹的模組，未來可以直接搬進真正的程式碼庫。頁面周圍的部分是可拋棄的；這個模組不是。

正確的形式取決於問題本身：

- **純粹的 reducer**：`(state, action) => state`。適合動作是離散事件、狀態是單一數值的情況。
- **狀態機**：明確的狀態與轉換。適合「現在哪些動作才是合法的」本身就是問題一部分的情況。
- **一組小型純函式**，作用於一個普通的資料型別。適合沒有隱含目前狀態、只有轉換操作的情況。
- **有明確方法介面的類別或模組**，當邏輯真的擁有持續存在的內部狀態時使用。

選擇最符合問題本身的形式，*而不是*最容易接到頁面上的形式。保持純粹：不碰 DOM、不用 `document`、按鈕的事件處理不能伸手進去改它。頁面呼叫它；不能反過來。這正是讓原型在自身生命週期結束後仍然有用的關鍵：一旦問題得到解答，經過驗證的 reducer／狀態機／函式集合就能直接搬進真正的模組。

### 3. 建立可分享的 HTML 檔案

單一檔案，純 HTML/CSS/JS：不用框架、不用打包工具、不用伺服器，全部內嵌，這樣雙擊就能開啟，也經得起用電子郵件轉寄。任何人都應該能直接打開來執行。

要為非開發人員而寫。每個標籤都使用**領域語言**，而不是程式碼術語：按鈕與狀態讀起來要像業務本身，而不是 reducer。用平實的文字解釋正在發生什麼事。

由上到下，用清楚的階層來排版：

1. **標題與一行說明**，說明這個展示讓你探索什麼問題（來自第一步的問題）。
2. **目前狀態**：所有相關的狀態，以易讀的面板呈現（要有標籤的欄位，不是原始的 JSON 傾印），每次點擊後都要重新渲染，讓變化清楚可見。在有助於非開發人員理解的地方，特別標示出剛剛發生了什麼變化。
3. **自由操作按鈕**：每個動作一個按鈕，隨時可用，讓任何人都能以任何順序去試探這個模型。每次點擊都會觸發對應的動作並重新渲染狀態。
4. **引導式演練**：一組**情境（scenarios）**，每個情境一個分頁。每個分頁裡有一段簡短、平實文字描述該情境（設定的狀況以及要注意觀察的重點），下方是該情境要**依序按下的按鈕**。每個步驟都是一個真正的按鈕：點擊就會執行該動作並移到下一步。開始一段演練時要重設回已知的初始狀態，這樣每次執行情境的結果都會一致。

選擇能凸顯棘手情況的情境，也就是那些在紙上很難推理清楚的情況：順利路徑、一個棘手的邊界情況，以及一次應該要被判定為不合法的嘗試。

保持美觀但克制：乾淨的排版、寬裕的留白、單一強調色。不要動畫、不要花招：不要有任何東西會跟狀態與按鈕搶注意力。

### 4. 交付

把檔案傳給對方，或直接幫他們打開。他們會在有空的時候點過各個演練並自由操作；有意思的時刻是他們說「等等，這應該不可能發生吧」或「咦，我以為 X 應該不一樣」的時候；那些正是*想法*本身的問題，也正是重點所在。如果他們想要新的動作或新的情境，就加進去。原型是會演進的。

### 5. 記錄下答案與原型

一旦原型回答了它的問題，先記錄下答案，然後依照 [SKILL](SKILL.md) 所描述的方式保存這個原型。針對邏輯類的對應方式：經過驗證的 reducer／狀態機／函式集合會被吸收進真正的模組（決策被納入）；HTML 外殼則歸入可拋棄分支，作為主要來源保留下來，而且因為它是單一個獨立檔案，在那裡也能輕鬆重新執行。

## 反模式

- **不要加測試。** 需要測試的原型就已經不是原型了。
- **不要接到真正的資料庫。** 除非問題本身就是關於持久化，否則用記憶體內狀態就好。
- **不要泛化。** 不要有「以後也許會想支援 X」這種念頭。原型只回答一個問題。
- **不要把邏輯和頁面混在一起。** 如果純粹的模組引用了 DOM、`document` 或按鈕的事件處理，它就不再是可搬移的了。頁面要維持只是包在純模組外層的一層薄殼。
- **不要用框架、打包工具或伺服器。** 一個檔案，收到的人雙擊就能開；React 應用或開發伺服器會破壞「可分享」這件事。
- **不要把 HTML 外殼放進正式環境。** 這個頁面是為了讓人手動點擊操作而最佳化的。背後的邏輯模組才是值得保留的部分。
