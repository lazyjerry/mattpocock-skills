# 原型 (Prototype)

原型是**用來回答問題的可拋棄程式碼**。問題決定了它的形式。

## 選擇分支

根據使用者的提示、周遭的程式碼，或直接詢問使用者是否在場，判斷目前要回答的是哪一個問題：

- **「這個邏輯 / 狀態模型感覺對嗎？」** → [LOGIC.md](LOGIC.md)。建立一個可分享的單一 HTML 檔案（包含自由操作按鈕，以及分頁式的引導走查），把狀態機推進到那些光靠紙上推演很難判斷的情境，而且要讓非開發者也能操作。
- **「這個東西應該長什麼樣子？」** → [UI.md](UI.md)。在同一個路由上產生多個截然不同的介面變化版本，透過 URL 查詢參數與浮動底部列來切換。

這兩個分支會產出非常不同的成果，所以一旦選錯分支就會浪費整個原型的心力。如果問題本身確實模稜兩可，而且使用者也聯絡不到，就預設選擇與周遭程式碼較相符的分支（後端模組 → 邏輯；頁面或元件 → 介面），並在原型最上方註明這個假設。

## 兩個分支都適用的規則

1. **從第一天起就是可拋棄的，而且要清楚標示。** 把原型程式碼放在實際會用到它的地方附近（緊鄰它要驗證的模組或頁面），讓脈絡一目了然，但命名要讓隨意瀏覽的人也能看出這是原型，而非正式程式碼。對於可拋棄的介面路由，要遵循專案既有的路由慣例，不要另外發明一套頂層結構。
2. **要能輕鬆執行。** 介面原型要能透過專案任務執行器的一個指令啟動：`pnpm <name>`、`python <path>`、`bun <path>` 等等。邏輯示範則是使用者雙擊即可開啟的單一 HTML 檔案。無論哪一種，都不需要動腦筋思考該怎麼啟動。
3. **預設不做持久化。** 狀態存放在記憶體中。持久化正是原型要_檢驗_的對象，不該是原型所依賴的東西。如果問題明確牽涉到資料庫，就使用一個測試用資料庫，或是命名清楚標示「PROTOTYPE, wipe me」的本地檔案。
4. **省略雕琢細節。** 不寫測試、不做超出讓原型_能跑起來_所需的錯誤處理、不做抽象化。重點是要快速學到東西。
5. **把狀態呈現出來。** 每次操作後（邏輯類）或每次切換變體時（介面類），都要印出或渲染出完整的相關狀態，讓使用者看得到發生了什麼變化。
6. **完成後把它保存下來。** 把任何已驗證的決策併入正式程式碼，然後把原型本身當作一份**原始資料**保存下來：提交到一個可拋棄的分支，獨立於 main 之外，並在實作議題上留一個指向該分支的脈絡連結。同時也要把結論（定案內容與它所解決的問題）記錄在議題或提交訊息中。main 分支只保留已驗證的決策。
