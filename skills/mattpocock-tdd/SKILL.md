# 測試驅動開發（Test-Driven Development）

TDD 是紅 → 綠的循環。這個技能是讓這個循環產出值得保留的測試的參考依據：什麼是好的測試、測試該放在哪裡、反模式，以及這個循環的規則。每個段落在每一輪循環都適用：在循環之前和期間都要參考它們，而不是事後才看。

在探索程式碼庫時，請閱讀 `CONTEXT.md`（如果存在的話），讓測試名稱與介面用詞能對齊專案的領域語言，並且尊重你所觸及範圍內的 ADR（架構決策紀錄）。

## 什麼是好的測試

測試應該透過公開介面來驗證行為，而不是驗證實作細節。程式碼可以徹底改變，但測試不應該跟著變。一個好的測試讀起來就像一份規格：「使用者可以用有效的購物車結帳」清楚地告訴你存在什麼樣的能力，而且它能在重構後依然存活，因為它不在意內部結構。

範例請參見 [tests.md](tests.md)，模擬（mocking）的指引請參見 [mocking.md](mocking.md)。

## 接縫（Seam）：測試該放在哪裡

**接縫（seam）**是你進行測試的公開邊界：也就是你能觀察行為、而不需要深入內部的那個介面。測試應該放在接縫上，絕對不要針對內部實作。

**只在事先議定的接縫上測試。** 在撰寫任何測試之前，先寫下受測的接縫，並與使用者確認。不會在未經確認的接縫上撰寫測試。你不可能測試所有東西，所以事先議定接縫，才能讓測試的心力落在關鍵路徑與複雜邏輯上，而不是每一個邊角案例。

問：「公開介面是什麼？我們該測試哪些接縫？」

當這個介面的形狀本身還有待討論時（模組該有多深、接縫該放在哪裡、介面該公開什麼），呼叫 Skill 工具並使用「mattpocock-codebase-design」來取得相關用詞。它是模組、介面、深度、接縫、轉接器（adapter）、槓桿（leverage）與局部性（locality）這些用詞的共同來源，是一份供你查閱的參考資料，而不是要你去執行的一個作業階段。

## 反模式

- **與實作耦合（Implementation-coupled）**：模擬內部協作物件、測試私有方法，或透過側邊管道驗證（例如直接查詢資料庫而不是使用介面）。判斷依據：當行為沒有改變、但重構後測試卻壞掉了。
- **套套邏輯（Tautological）**：斷言用和程式碼相同的方式重新計算出預期值（例如 `expect(add(a, b)).toBe(a + b)`、以相同方式手動推導出來的快照、斷言一個常數等於它自己），因此它必然通過，永遠不可能與程式碼產生分歧。預期值必須來自獨立的真實依據：一個已知正確的字面值、一個實際運算過的範例、或規格文件。
- **水平切片（Horizontal slicing）**：先寫完所有測試，再寫所有實作。大量測試驗證的是_想像中的_行為：你測試的是事物的_外形_，而不是使用者面向的行為，這些測試會對真正的變化變得不敏感，而且你在還沒理解實作之前，就先確定了測試結構。應該改用**垂直切片（vertical slices）**：一個測試 → 一個實作 → 重複，每個測試都是一發**曳光彈（tracer bullet）**，回應上一輪循環所教你的東西。

## 循環的規則

- **先紅後綠。** 先寫失敗的測試，然後只寫剛好足以讓它通過的程式碼。不要預先設想未來的測試，也不要加入投機性的功能。
- **一次一個切片。** 每一輪循環只處理一個接縫、一個測試、一個最小實作。
- **重構不是這個循環的一部分。** 它屬於審查階段（參見 `/code-review`），而不是紅 → 綠的實作循環。
