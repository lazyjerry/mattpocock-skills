在 `HEAD` 與使用者提供的固定點之間的 diff 進行雙軸檢視：

- **Standards**：程式碼是否符合此 repo 記載的程式碼規範？
- **Spec**：程式碼是否忠實實作了原始的 issue／spec？

兩個軸線都以**平行子代理**執行，避免彼此的內容互相污染，接著本 skill 會彙整兩者的發現。

issue tracker 應該已經提供給你了。若 `docs/agents/issue-tracker.md` 不存在，請告知使用者執行 `/setup-matt-pocock-skills`。

## 流程

### 1. 釘選固定點

無論使用者說的固定點是什麼（commit SHA、分支名稱、標籤、`main`、`HEAD~5` 等）。若未指定，請詢問。

一次記下 diff 指令：`git diff <fixed-point>...HEAD`（三點語法，這樣比較的對象會是 merge-base）。也要記下 commit 清單：`git log <fixed-point>..HEAD --oneline`。

在繼續進行之前，先確認固定點能被解析（`git rev-parse <fixed-point>`）且 diff 非空。錯誤的 ref 或空的 diff 應該在這一步就失敗，而不是在兩個平行子代理裡面才發現。

### 2. 找出 spec 來源

依照以下順序尋找原始 spec：

1. commit 訊息中的 issue 參照（`#123`、`Closes #45`、GitLab `!67` 等），透過 `docs/agents/issue-tracker.md` 所述的流程取得。
2. 使用者以參數傳入的路徑。
3. `docs/`、`specs/` 或 `.scratch/` 底下，符合分支名稱或功能的 spec 檔案。
4. 若都找不到，詢問使用者 spec 在哪裡。若對方表示沒有 spec，**Spec** 子代理會跳過並回報「沒有可用的 spec」。

### 3. 找出 standards 來源

repo 中任何記載程式碼撰寫方式的檔案，例如 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md`。

除了 repo 記載的內容之外，Standards 軸線一律會額外納入以下**程式碼異味基準線**：一組固定的 Fowler code smells（出自《Refactoring》第 3 章），即使 repo 完全沒有文件記載也適用。這裡有兩條規則：

- **repo 優先。** 記載於 repo 的規範永遠優先；若某個做法被 repo 規範認可，即使基準線會標記它，也應該予以忽略。
- **一律屬於判斷性意見。** 每個 smell 都是一個帶標籤的啟發式提示（例如「疑似 Feature Envy」），從來不是硬性違規。就像本文件中的其他規範一樣，只要是工具已經強制檢查的項目，就跳過。

每個 smell 都依「*它是什麼*」→「*如何修正*」的方式呈現；請對照 diff 逐一比對：

- **Mysterious Name（名稱不明）**：函式、變數或型別的名稱無法表達其用途或內容。→ 重新命名；若想不出誠實的名稱，代表設計本身還不清楚。
- **Duplicated Code（重複程式碼）**：同樣的邏輯形狀出現在不只一個 hunk 或檔案的變更中。→ 抽出共用的邏輯形狀，讓兩處都呼叫它。
- **Feature Envy（依戀情結）**：某個方法存取另一個物件的資料，遠多於存取自己的資料。→ 把方法搬到它所依戀的資料所在之處。
- **Data Clumps（資料泥團）**：同一組欄位或參數總是一起出現（一個渴望誕生的型別）。→ 將它們打包成一個型別，改傳遞這個型別。
- **Primitive Obsession（基本型別偏執）**：以基本型別或字串代表一個值得擁有自己型別的領域概念。→ 為該概念建立一個小型專屬型別。
- **Repeated Switches（重複的分支判斷）**：對同一型別做的相同 `switch`／`if` 串接，在變更中重複出現。→ 改用多型，或讓兩處共用同一份對照表。
- **Shotgun Surgery（散彈式修改）**：一項邏輯變更卻迫使 diff 中散布多個檔案都要跟著修改。→ 把會一起變動的內容收攏進同一個模組。
- **Divergent Change（發散式變更）**：同一個檔案或模組因為多個不相關的原因而被修改。→ 拆分模組，讓每個模組只因單一原因而變動。
- **Speculative Generality（多餘的一般化）**：為了 spec 並未要求的需求而加入的抽象、參數或掛勾點。→ 刪除它，等到真正有需求時再內聯回去。
- **Message Chains（訊息鏈）**：呼叫端不該依賴的一長串 `a.b().c().d()` 導覽式呼叫。→ 把整條導覽路徑藏到第一個物件的一個方法背後。
- **Middle Man（中間人）**：一個大多只是把工作轉手出去的類別或函式。→ 移除它，直接呼叫真正的目標。
- **Refused Bequest（拒絕繼承）**：子類別或實作者忽略或覆寫了大部分繼承而來的內容。→ 移除繼承關係，改用組合。

### 4. 平行啟動兩個子代理

**Standards 子代理提示**應包含：

- 完整的 diff 指令與 commit 清單。
- 第 3 步驟中找到的 standards 來源檔案清單，**再加上第 3 步驟的完整 smell 基準線內容**（子代理沒有其他管道能取得這份內容）。
- 任務說明：「請依檔案／hunk 逐項回報：(a) diff 中每一處違反已記載規範的地方：引用該規範（檔案＋規則）；以及 (b) 你發現的任何基準線 smell：命名它並引用該段 hunk。請區分硬性違規與判斷性意見：違反已記載規範可以算是硬性違規，但基準線 smell 一律屬於判斷性意見，且 repo 記載的規範優先於基準線。跳過工具已強制檢查的項目。字數限制 400 字以內。」

**Spec 子代理提示**應包含：

- diff 指令與 commit 清單。
- spec 的路徑或取得的內容。
- 任務說明：「請回報：(a) spec 要求但缺漏或未完整實作的需求；(b) diff 中出現但未被要求的行為（範圍蔓延）；(c) 看似已實作但實作方式有誤的需求。每項發現都請引用對應的 spec 文字。字數限制 400 字以內。」

若 spec 不存在，跳過 Spec 子代理，並在最終報告中註明此情形。

### 5. 彙整

在 `## Standards` 與 `## Spec` 標題下，逐字或稍加整理地呈現兩份報告。**不要**合併或重新排序發現項目，因為這兩個軸線是刻意分開的（詳見 _為什麼要分兩個軸線_）。

最後以一行摘要總結：各軸線的發現總數，以及**各軸線內部**最嚴重的問題（如果有的話）。不要跨軸線挑出單一「最嚴重」的問題，那正是分軸機制想避免的重新排序行為。

## 為什麼要分兩個軸線

一項變更可能通過其中一個軸線，卻在另一個軸線失敗：

- 完全遵循規範，但實作了錯誤的東西 → **Standards 通過，Spec 失敗。**
- 完全按照 issue 要求實作，卻破壞了專案的慣例 → **Spec 通過，Standards 失敗。**

分開回報能避免其中一個軸線掩蓋另一個軸線的問題。
