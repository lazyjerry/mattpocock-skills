# UI 原型

在單一路由上產生**數個截然不同的 UI 變化版本**，並透過一個浮動於畫面底部的工具列進行切換。使用者可以在瀏覽器中來回切換各個變體，選出其中一個（或從各個版本中挑選喜歡的部分），然後把其餘的丟掉。

如果問題是關於邏輯 / 狀態，而非畫面外觀，那麼這份文件不適用。請改用 [LOGIC.md](LOGIC.md)。

## 適用此做法的情境

- 「這個頁面看起來應該長怎樣？」
- 「我想在確定方向之前，先看看這個儀表板的幾個選項。」
- 「幫設定畫面試試不同的版面配置。」
- 任何使用者原本得花一整天在腦中比較三個模糊模型稿的情況。

## 兩種子模式：強烈建議優先採用子模式 A

當 UI 原型**與應用程式其餘部分緊密結合**時，會更容易判斷好壞：真實的標頭（header）、真實的側邊欄、真實的資料、真實的密度。一個獨立存在的臨時路由等於是真空狀態：每個變體單獨看起來都不錯。只要有合適的既有頁面可以承載這些變體，就預設採用子模式 A。只有在原型真的沒有適合的位置可放時，才使用子模式 B。

### 子模式 A：調整既有頁面（建議做法）

路由本身已經存在。變體會渲染在**同一個路由上**，以 `?variant=` 這個 URL 查詢參數來控制顯示哪一個。既有的資料抓取、參數、身分驗證都維持不變，只有渲染的內容會切換。這是預設做法，除非有特定理由不這麼做，否則就選這個。

如果原型是為了尚未有頁面、但*自然會存在於某個頁面內*的東西（儀表板的新區塊、設定畫面上的新卡片、既有流程中的新步驟），那仍然屬於子模式 A。把這些變體掛載到承載它們的既有頁面內。

### 子模式 B：全新頁面（最後手段）

只有在要製作原型的東西真的沒有既有頁面可以承載時才使用（例如全新的頂層畫面，或是無法合理內嵌到任何地方的流程）。

依照專案已經在使用的路由慣例，建立一個**用完即丟的路由**。不要另外發明一套新的頂層結構。命名時要讓人一看就知道這是原型(例如路徑或檔名中包含 `prototype` 這個字)。同樣採用 `?variant=` 的模式。

在決定採用子模式 B 之前，先做個檢查：真的沒有既有頁面可以內嵌這個原型嗎？一個空蕩蕩的路由會掩蓋掉一個已填滿內容的頁面才會暴露出來的設計問題。

不論哪一種子模式，浮動底部工具列都是完全相同的。

## 流程

### 1. 明確寫出問題並決定變體數量 N

預設為 **3 個變體**。超過 5 個就不再算是「截然不同」，而會變成雜訊，所以請以此為上限。

在原型所在位置或檔案最上方的註解中，用一行寫下計畫：

> 「設定頁面的三個變體，透過 `?variant=` 切換，建立在既有的 `/settings` 路由上。」

不論使用者是要來反駁還是要照做，這一步都會有幫助。

### 2. 產生截然不同的變體

草擬每一個變體。每個變體都要符合以下要求：

- 符合此頁面的用途以及它能存取的資料。
- 符合此專案的元件庫 / 樣式系統（TailwindCSS、shadcn、MUI、純 CSS，不論是哪一種）。
- 有清楚匯出的元件名稱，例如 `VariantA`、`VariantB`、`VariantC`。

各變體之間必須**在結構上有明顯差異**：不同的版面配置、不同的資訊層級、不同的主要互動方式，而不只是顏色不同。三個只是略微調整的卡片格線並不是 UI 原型，而是壁紙。如果有兩個草稿看起來太相似，就把其中一個重做，並明確給出像是「不要使用卡片格線」這樣的指示。

### 3. 把它們串接起來

在該路由上建立一個單一的切換元件：

```tsx
// pseudo-code, adapt to the project's framework
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

對於子模式 A（既有頁面）：讓所有既有的資料抓取邏輯留在切換元件的上層；只有渲染出來的子樹會依變體不同而改變。

對於子模式 B（新頁面）：位於 `/prototype/<name>` 底下的臨時路由掛載相同的切換元件。

### 4. 建立浮動切換工具列

一個固定位置、位於畫面底部置中的小工具列，包含三個部分：

- **左箭頭**：切換到上一個變體（循環，到頭後回到最後一個）。
- **變體標籤**：顯示目前的變體代號，如果該變體有匯出名稱，也一併顯示。例如 `B (Sidebar layout)`。
- **右箭頭**：切換到下一個變體（循環）。

行為方式：

- 點擊箭頭時，要透過該框架的路由機制(例如 Next.js 的 `router.replace`、React Router 的 `navigate` 等)更新 URL 查詢參數，讓變體可以被分享，重新整理後也能保留狀態。
- 鍵盤操作：`←` 和 `→` 方向鍵也可以切換變體。但當 `<input>`、`<textarea>` 或 `[contenteditable]` 元素處於聚焦狀態時，不要攔截方向鍵。
- 視覺上要與頁面本身有明顯區隔（例如高對比的膠囊形狀、淡淡的陰影），讓人一看就知道這不是正在被評估的設計本身的一部分。
- 在正式環境版本中要隱藏：以 `process.env.NODE_ENV !== 'production'` 或等效的判斷式來控制顯示與否，避免不小心把原型合併進主線後，這個工具列被一併上線給使用者看到。

把切換工具列放在一個共用元件中，讓兩種子模式都能重複使用。放在該專案存放共用 UI 元件的位置。

### 5. 交付成果

提供該 URL(以及 `?variant=` 的各個代號)。使用者有空時會自行來回切換查看。通常最有價值的回饋會是「我想要 B 的標頭配上 C 的側邊欄」這種說法，而這其實就是使用者真正想要的設計。

### 6. 記錄結論並清理

一旦確定哪個變體勝出，先記錄下結論（選了哪一個變體、原因是什麼），接著依照 [SKILL](SKILL.md) 所描述的方式保存這個原型。把勝出的版本整合進正式程式碼，其餘的則移到用完即丟的分支上，而不是留在 main:

- **子模式 A**：把勝出的版本整合進既有頁面；從 main 分支中移除落敗的變體以及切換元件。
- **子模式 B**：把勝出的變體升級為正式路由；從 main 分支中移除臨時路由以及切換元件。

完整的變體集合才是主要的參考來源，所以它應該留在用完即丟的分支上，而不是直接刪除，因為留在 main 分支裡的變體元件和切換元件會很快過時，並讓下一個閱讀程式碼的人感到困惑。

## 反面模式（應避免的做法）

- **變體之間只有顏色或文案不同。** 那只是微調，不是原型。真正的變體在結構上就應該不一樣。
- **變體之間共用過多程式碼。** 共用一個 `<Header>` 沒問題；但共用一個 `<Layout>` 就違背了原本的目的。每個變體都應該可以自由捨棄版面配置，重新設計。
- **把變體接上真實的資料變更（mutation）操作。** 唯讀的原型沒問題。如果某個變體需要進行資料變更，就讓它指向一個假的（stub）實作：此階段要回答的問題是「這應該長什麼樣子」，而不是「後端功能是否正常運作」。
- **直接把原型升級成正式上線的版本。** 原型程式碼是在原型階段的限制下寫成的（沒有測試、錯誤處理也很陽春）。在把它整合進正式程式碼時，要重新用正式的標準把它寫好。
