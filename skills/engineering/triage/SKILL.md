# Triage（分類處理）

在專案的議題追蹤系統中，將 issue 依照一套小型狀態機推進處理角色。

如果這個 repo 將外部 pull request 視為請求來源之一（詳見 issue-tracker 設定），triage 也涵蓋這些 PR：**PR 就是附帶程式碼的 issue**，使用相同的角色、相同的狀態、相同的機制，僅在以下標示「針對 PR」的地方有些許差異。依照 tracker 設定，將單純的 `#42` 解析為對應的 issue 或 PR。

在 triage 過程中，發佈到議題追蹤系統的每一則留言或 issue，**都必須**以下列免責聲明開頭：

```
> *This was generated by AI during triage.*
```

## 參考文件

- [AGENT-BRIEF.md](AGENT-BRIEF.md)：如何撰寫可長期沿用的 agent 簡報
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)：`.out-of-scope/` 知識庫的運作方式

## 角色

兩種**分類（category）**角色：

- `bug`：某個東西壞掉了
- `enhancement`：新功能或改善項目

五種**狀態（state）**角色：

- `needs-triage`：維護者需要評估
- `needs-info`：等待回報者提供更多資訊
- `ready-for-agent`：規格已完整，可交給 AFK agent 處理
- `ready-for-human`：需要由人來實作
- `wontfix`：不會被處理

對於 PR，同樣的狀態對應到附帶的程式碼上：`ready-for-agent` 表示簡報已附上，agent 應對該 diff 採取下一步行動；`ready-for-human` 表示已準備好讓人來合併。

每個經過 triage 的 issue，都應該剛好帶有一個分類角色與一個狀態角色。若狀態角色互相衝突，先標記出來並詢問維護者，再進行任何動作。

這些是標準（canonical）角色名稱。議題追蹤系統中實際使用的標籤字串可能不同，其對應關係應該已經提供給你。如果沒有，請告知使用者執行 `/setup-matt-pocock-skills`。

狀態轉換：未標記的 issue 通常會先進入 `needs-triage`；接著再轉為 `needs-info`、`ready-for-agent`、`ready-for-human`，或 `wontfix`。當回報者回覆後，`needs-info` 會回到 `needs-triage`。維護者可隨時覆寫這個流程；若轉換看起來不尋常，先標記並詢問後再繼續。

## 呼叫方式

維護者呼叫 `/triage` 並以自然語言描述需求，你需解讀後採取行動。範例：

- 「顯示需要我處理的項目」
- 「來看一下 #42」（issue 或 PR）
- 「把 #42 移到 ready-for-agent」
- 「有哪些已經可以交給 agent 處理？」

## 顯示需要關注的項目

查詢議題追蹤系統，依由舊到新的順序呈現三個區塊：

1. **未標記（Unlabeled）**：從未經過 triage。
2. **`needs-triage`**：評估進行中。
3. **`needs-info` 且回報者在上次 triage 筆記之後有活動**：需要重新評估。

若 PR 也在範圍內，將外部 PR 也納入這些區塊中，並在每一行標註 `[PR]` 或 `[issue]`。探索階段只會列出*外部*的 PR（誰算外部由 tracker 設定決定），因此協作者正在進行中的 PR 不會被列入 triage 工作。這個過濾僅適用於探索階段；只要是明確點名的 PR，一律會進行 triage。

顯示各區塊的數量與每個項目的一行摘要，讓維護者自行挑選。

## 對特定的 issue 或 PR 進行 triage

1. **蒐集脈絡。** 讀取完整的 issue 或 PR（內文、留言、標籤、作者、日期；若是 PR，也要看 diff）。解析先前的 triage 筆記，避免重複詢問已解決的問題。使用專案的領域術語探索程式碼庫，並遵守該區域既有的 ADR。對程式碼庫執行兩項檢查：(a) **重複性檢查**：依照領域概念（而非只依照請求的字面用詞）搜尋是否已有實作該行為的既有程式碼，並回報你查找過的位置。若已存在，則歸類為已實作的 `wontfix`（見步驟 5）。(b) **先前是否已被否決**：閱讀 `.out-of-scope/*.md`，找出與此請求類似的紀錄。

2. **提出建議。** 向維護者說明你建議的分類與狀態，並附上理由，以及與此請求相關的程式碼庫摘要（包含是否已經實作）。等待維護者指示後再繼續。

3. **驗證此主張。** 在進行任何追問之前，先確認此主張是否成立。若為 bug，依照回報者提供的步驟重現；若為 PR，確認該 diff 確實達成其宣稱的效果：checkout 該分支，執行相關測試或指令。回報結果：已確認（附上程式碼路徑）、失敗，或資訊不足（這是強烈的 `needs-info` 訊號）。經確認的驗證能讓 agent 簡報更有說服力。

4. **追問細節（如有需要）。** 若此請求需要進一步充實內容，分別呼叫 Skill 工具兩次，使用 "grilling" 與 "domain-modeling"，一輪一輪地追問細節使其成形，同時釐清領域術語，並隨著決策底定即時更新 `CONTEXT.md`／ADR。

5. **套用結果：**
   - `ready-for-agent`：發佈一則 agent 簡報留言（見 [AGENT-BRIEF.md](AGENT-BRIEF.md)）。
   - `ready-for-human`：結構與 agent 簡報相同，但需註明為何無法委派（需要人為判斷、外部存取權限、設計決策、人工測試等）。
   - `needs-info`：發佈 triage 筆記（範本如下）。
   - 對於 `wontfix`，關閉該 issue，留言內容依*原因*而定：
     - **已實作**：該變更在程式碼庫中已存在。指出其所在位置；**不要**寫入 `.out-of-scope/`（該知識庫是給*被否決*的請求用的，不是給已完成的功能用的）。
     - **被否決（bug）**：給出禮貌的說明後關閉。
     - **被否決（enhancement）**：寫入 `.out-of-scope/`，在留言中附上連結，然後關閉（見 [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)）。
   - `needs-triage`：套用此角色。若有部分進度，可附上留言（非必要）。

## 快速覆寫狀態

若維護者說「把 #42 移到 ready-for-agent」，直接信任並套用該角色。先確認即將執行的動作（角色變更、留言、關閉），再執行。跳過追問步驟。若在未經追問的情況下移到 `ready-for-agent`，先詢問是否需要撰寫 agent 簡報。

## Needs-info 範本

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

將追問過程中已釐清的內容全部記錄在「established so far」中，避免相關成果流失。問題必須具體且可行動，而非「請提供更多資訊」這類空泛的說法。

## 接續先前的 session

若該 issue 或 PR 上已有先前的 triage 筆記，先讀取，確認回報者是否已回覆先前未解決的問題，並在繼續前呈現更新後的現況。不要重複詢問已解決的問題。
