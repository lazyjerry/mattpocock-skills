# To Tickets

將計畫、規格書或對話拆解成一組**工單（tickets）**：tracer-bullet 式的垂直切片，每張工單都聲明會**阻擋（block）**它的其他工單。

議題追蹤系統與分流標籤詞彙應該已經提供給你。如果沒有，請執行 `/setup-matt-pocock-skills`。

## 流程

### 1. 蒐集脈絡

從對話脈絡中既有的內容著手。如果使用者傳入參考資料作為參數（規格書路徑、議題編號或網址），請取得並閱讀其完整內容與留言。

### 2. 探索程式碼庫（選用）

如果你還沒探索過程式碼庫，請先探索以了解目前的程式碼狀態。工單標題與描述應使用該專案的領域詞彙，並遵守你所觸及區域的 ADR。

尋找可以先做「預先重構（prefactor）」的機會，讓後續實作更容易。「先讓變更變得容易，再做這個容易的變更。」

### 3. 草擬垂直切片

將工作拆解成**tracer bullet** 工單。

<vertical-slice-rules>

- 每個切片都貫穿每一層（schema、API、UI、測試）走出一條窄但完整的路徑：是垂直的，而不是單一層的水平切片
- 完成的切片本身就能展示或驗證
- 每個切片的大小要能塞進單一個全新的 context window
- 任何預先重構都應該先完成

</vertical-slice-rules>

給每張工單它的**阻擋邊（blocking edges）**：也就是必須先完成才能開始這張工單的其他工單。沒有阻擋者的工單可以立即開始。

**大範圍重構是垂直切片的例外情況。** **大範圍重構（wide refactor）**指的是單一機械式變更（重新命名欄位、更改共用符號的型別），其**影響範圍（blast radius）**擴及整個程式碼庫，因此單一次編輯會同時破壞數千個呼叫點，沒有任何垂直切片能夠順利通過（land green）。不要硬把它塞進 tracer bullet 裡，而是應該用**擴張與收斂（expand-contract）**的方式排序。先擴張：在舊形式旁加入新形式，確保不會破壞任何東西。接著分批遷移呼叫點，批次大小依影響範圍而定（依套件、依目錄），每一批各自成為一張工單，並被「擴張」那張工單阻擋，如此可讓每批之間 CI 都維持綠燈，因為舊形式仍然存在。最後收斂：等沒有任何呼叫者還在用舊形式後，用一張工單刪除舊形式，這張工單被所有遷移批次阻擋。當即使分批也無法各自維持綠燈時，仍維持這個順序，但讓這些批次共用一條整合分支，全部阻擋最後一張「整合並驗證」的工單；綠燈只在那張工單上才被保證。

### 4. 向使用者確認

以編號清單呈現提議的拆解結果。針對每張工單，顯示：

- **標題（Title）**：簡短的描述性名稱
- **受阻於**：哪些其他工單（如果有的話）必須先完成
- **交付內容（What it delivers）**：這張工單讓哪個端到端行為可以運作

詢問使用者：

- 拆解的粒度是否恰當？（太粗 / 太細）
- 阻擋邊是否正確：每張工單是否只依賴真正卡住它的工單？
- 是否有工單應該合併或再進一步拆分？

反覆調整，直到使用者核准這份拆解結果。

### 5. 將工單發布到設定好的追蹤系統

發布已核准的工單。**如何**發布取決於 `/setup-matt-pocock-skills` 設定的追蹤系統；不論哪種情況工單內容都相同，只有阻擋邊的呈現形式不同：

- **本機檔案** → 在 `.scratch/<feature-slug>/issues/<NN>-<slug>.md` 底下為每張工單寫一個檔案，依相依順序（阻擋者優先）從 `01` 開始編號。每個檔案的「受阻於」要列出它所依賴的編號/標題。使用下方的單一工單檔案範本：一個檔案只放一張工單，絕不要放進單一合併檔案。
- **真正的議題追蹤系統（GitHub、Linear 等）** → 依相依順序（阻擋者優先）為每張工單發布一個議題，讓每張工單的阻擋邊可以參照真實的識別碼。若平台有原生的阻擋／子議題（sub-issue）關聯功能就使用它；否則將每張工單的「受阻於」設為阻擋它的議題。除非另有指示，否則套用 `ready-for-agent` 分流標籤；這些工單本質上就是可讓 agent 直接領取的。

以**前緣（frontier）**方式進行：也就是所有阻擋者都已完成的任何工單。對於單純線性的鏈狀結構，這代表由上而下依序處理。

**請勿**關閉或修改任何父議題。
