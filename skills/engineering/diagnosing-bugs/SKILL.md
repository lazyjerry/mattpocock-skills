# 診斷錯誤

一套用來處理困難錯誤的紀律。只有在有明確理由時才跳過某個階段。

在探索程式碼庫時，先閱讀 `CONTEXT.md`（若存在）以建立你正在處理模組的清楚心智模型，並檢查你要動到的區域相關的 ADR。

## 遮蔽機密資訊

這個技能會要求你顯示指令、輸出結果與擷取到的產出物。**先遮蔽所有機密資訊**：在原本位置寫上 `<REDACTED>`。建構迴圈時使用環境變數，讓憑證留在環境中，而不是出現在你展示的內容裡。擷取到的產出物帶有驗證標頭：只引用帶有關鍵訊號的那幾行。

如果遮蔽後的輸出不足以診斷錯誤，就明確說明，並詢問使用者。

## 第一階段：建立回饋迴圈

**這就是這個技能的核心。** 其他一切都只是機械式執行。如果你有一個**緊湊**的通過/失敗訊號能對應到這個錯誤（能在_這個_錯誤上變紅），你就會找到原因；二分搜尋、假設驗證、插入偵錯探針全都只是在消耗這個訊號。如果你沒有這個訊號，再怎麼盯著程式碼看也沒用。

在這裡投入不成比例的心力。**要積極、要有創意、絕不放棄。**

### 建立回饋迴圈的方式，大致依此順序

1. **失敗測試**，設在任何碰得到這個錯誤的接縫（seam）：單元測試、整合測試、端對端測試。
2. **Curl / HTTP 腳本**，對著正在執行的開發伺服器發送請求。
3. **CLI 呼叫**，帶入固定測試資料（fixture），再將 stdout 與已知正確的快照做差異比對。
4. **無頭瀏覽器腳本**（Playwright / Puppeteer），驅動 UI 並斷言 DOM／console／network 的狀態。
5. **重播擷取到的追蹤紀錄。** 把真實的網路請求／payload／事件記錄存到磁碟，再獨立重播進該段程式碼路徑。
6. **拋棄式測試框架（Throwaway harness）。** 啟動系統的一個最小子集（單一服務、模擬依賴），用單一函式呼叫觸發錯誤的程式碼路徑。
7. **屬性測試／模糊測試迴圈。** 如果錯誤是「有時輸出錯誤」，就跑 1000 個隨機輸入，找出失敗模式。
8. **二分搜尋測試框架。** 如果錯誤是在兩個已知狀態之間出現的（commit、資料集、版本），把「在狀態 X 啟動、檢查、重複」這個流程自動化，讓你可以用 `git bisect run` 執行。
9. **差異比對迴圈。** 用同一份輸入分別跑舊版本與新版本（或兩種設定），比對輸出差異。
10. **HITL bash 腳本。** 最後手段。如果一定要有人手動點擊，就用 `scripts/hitl-loop.template.sh` 來驅動_那個人_，讓這個迴圈仍然是有結構的。擷取到的輸出會回饋給你。

建立正確的回饋迴圈，錯誤就已經解決了九成。

### 收緊迴圈

把這個迴圈當成一項產品來對待。一旦有了_某個_迴圈，就要**收緊**它：

- 能不能讓它更快？（快取設定、跳過不相關的初始化、縮小測試範圍。）
- 能不能讓訊號更精準？（斷言在具體的症狀上，而不是「沒有當掉」。）
- 能不能讓它更具決定性？（固定時間、設定亂數種子、隔離檔案系統、凍結網路。）

一個 30 秒但不穩定的迴圈，跟完全沒有迴圈比起來好不了多少；一個 2 秒且具決定性的迴圈，才是緊湊的，是除錯上的殺手鐧。

### 非決定性錯誤

目標不是乾淨的重現方式，而是**提高重現機率**。把觸發條件迴圈跑 100 次、平行化、加入壓力測試、縮小時間窗、插入延遲（sleep）。有 50% 出現機率的錯誤是可以除錯的；1% 的則不行，所以要持續提高機率，直到可以除錯為止。

### 當你真的無法建立迴圈時

停下來，明確說明這一點。列出你嘗試過的方法。向使用者請求：(a) 能重現問題的環境存取權限，(b) 已遮蔽機密資訊的擷取產出物（HAR 檔案、日誌傾印、core dump、附時間戳記的螢幕錄影），或 (c) 允許在正式環境加入暫時性的偵錯機制。**不要**在沒有迴圈的情況下就直接開始提出假設。

### 完成標準：一個能變紅的緊湊迴圈

第一階段完成的條件是：迴圈是**緊湊**且**能變紅**的，也就是你能指出**一個指令**（腳本路徑、測試呼叫、curl 指令），而且你**已經至少執行過一次**（展示該呼叫及其輸出，並已遮蔽機密資訊），並且符合以下條件：

- [ ] **能變紅**：它會驅動實際的錯誤程式碼路徑，並斷言**使用者描述的確切症狀**，因此它能在這個錯誤上變紅、在修復後變綠。不是「執行時沒有報錯」，而是必須能_捕捉到這個特定的錯誤_。
- [ ] **具決定性**：每次執行結果一致（對於不穩定的錯誤：依前述方式固定並提高重現機率）。
- [ ] **快速**：以秒為單位，而非分鐘。
- [ ] **可由代理程式執行**：你可以無人值守地執行它；只有透過 `scripts/hitl-loop.template.sh` 才能讓人類參與迴圈。

如果你發現自己在這個指令存在之前就開始讀程式碼、建立理論，**停下來：直接跳到假設，正是這個技能要防止的失敗模式。** 沒有能變紅的指令，就不能進入第二階段。

## 第二階段：重現並最小化

執行這個迴圈。觀察錯誤出現時它變紅。

確認：

- [ ] 這個迴圈重現的是**使用者**描述的失敗模式，而不是恰好在附近的另一個失敗。抓錯錯誤 = 修錯方向。
- [ ] 這個失敗在多次執行中都能重現（對於非決定性錯誤，則是以足夠高的機率重現，能拿來除錯）。
- [ ] 你已擷取到確切的症狀（錯誤訊息、錯誤輸出、時間過長），以便後續階段能驗證修復確實解決了問題。

### 最小化

一旦迴圈變紅，就把重現方式縮小到**仍能變紅的最小情境**。**一次只刪除一項**輸入、呼叫方、設定、資料、步驟，每刪除一項就重新執行迴圈，只保留對觸發失敗來說是必要的部分。

為什麼要這麼做：一個最小化的重現方式，能縮小第三階段的假設空間（剩下需要懷疑的變動部分更少），也會成為第五階段乾淨的回歸測試。

當**剩下的每一個元素都是必要的**時，就算完成：移除其中任何一項都會讓迴圈變綠。

在你重現**且**最小化之前，不要繼續進行下一步。

## 第三階段：提出假設

在測試任何一個假設之前，先產生 **3 到 5 個排序過的假設**。只產生單一假設，會讓你被第一個看似合理的想法定錨。

每個假設都必須是**可證偽的**：說明它會做出什麼預測。

> 格式：「如果 <X> 是原因，那麼<改變 Y> 會讓錯誤消失／<改變 Z> 會讓情況變得更糟。」

如果你無法說出這個預測，這個假設就只是憑感覺，應該捨棄或加以精煉。

**在測試之前，把排序過的清單展示給使用者看。** 他們通常擁有能立即重新排序清單的領域知識（例如「我們剛部署了第 3 項的變更」），或知道哪些假設他們已經排除過了。這是一個成本很低、卻能節省大量時間的檢查點。不需要因此卡住；如果使用者不在，就照你自己的排序繼續進行。

## 第四階段：插入偵錯機制

每個探針都必須對應到第三階段中的一個具體預測。**一次只改變一個變數。**

工具優先順序：

1. 如果環境支援，優先使用**除錯器／REPL 檢查**。一個中斷點勝過十個日誌輸出。
2. **針對性的日誌**，設在能區分各假設的邊界上。
3. 絕不要「把所有東西都記錄下來，然後用 grep 去找」。

**為每一條偵錯日誌加上標籤**，例如唯一前綴 `[DEBUG-a4f2]`。這樣一來，最後的清理工作只需要一次 grep 就能完成。沒有標籤的日誌會留下來；有標籤的日誌會被清除。

**效能分支。** 對於效能回歸問題，日誌通常沒什麼用。應該改為：先建立基準測量值（計時測試框架、`performance.now()`、效能分析器、查詢計畫），再進行二分搜尋。先測量，再修復。

## 第五階段：修復並撰寫回歸測試

**在修復之前**先寫好回歸測試，但前提是必須有一個**正確的接縫**。

正確的接縫，是指該測試能在呼叫端實際發生的情況下，重現**真實的錯誤模式**。如果唯一能用的接縫太淺（例如錯誤需要多個呼叫方才會出現，但只有單一呼叫方的測試；或是無法重現觸發錯誤那條呼叫鏈的單元測試），在那裡寫回歸測試只會給人一種錯誤的安心感。

**如果不存在正確的接縫，這件事本身就是一項發現。** 把它記錄下來。這代表程式碼庫的架構本身阻礙了對這個錯誤的鎖定。把這一點標記出來，留給下一階段處理。

如果存在正確的接縫：

1. 把最小化後的重現方式，轉換成該接縫上的一個失敗測試。
2. 觀察它失敗。
3. 套用修復。
4. 觀察它通過。
5. 針對原始（未最小化）的情境，重新執行第一階段的回饋迴圈。

## 第六階段：清理與事後檢討

宣告完成前，必須完成以下事項：

- [ ] 原始的重現方式已無法再重現（重新執行第一階段的迴圈）
- [ ] 回歸測試通過（或已記錄不存在接縫的情況）
- [ ] 所有 `[DEBUG-...]` 偵錯機制皆已移除（`grep` 該前綴確認）
- [ ] 拋棄式的原型（prototype）皆已刪除（或移至明確標示的偵錯位置）
- [ ] 在 commit / PR 訊息中說明最終證實正確的那個假設，讓下一個除錯的人能從中學到經驗

**接著問：什麼可以預防這個錯誤？** 如果答案牽涉到架構上的改變（沒有好的測試接縫、呼叫端糾結、隱藏的耦合），就帶著具體細節交給 `/improve-codebase-architecture` 技能。這項建議要在修復完成**之後**才提，不是之前：你現在掌握的資訊比一開始多。
