# Codebase Design

設計**深層模組（deep modules）**：在小巧的介面背後藏有大量行為，設置在乾淨的接縫（seam）上，並可透過該介面進行測試。無論何時在設計或重構程式碼，都應使用這套語言與這些原則。目標是為呼叫方帶來槓桿效益、為維護者帶來局部性，並讓所有人都能輕鬆測試。

## 詞彙表

請精確使用以下詞彙：不要用「component」、「service」、「API」或「boundary」取代。用詞一致正是重點所在。

**模組（Module）**：任何具有介面與實作的東西。刻意採用與規模無關的定義：可以是一個函式、類別、套件，或跨越多層的一整段程式。_避免使用_：unit、component、service。

**介面（Interface）**：呼叫方要正確使用該模組所必須知道的一切：不只是型別簽章，還包括不變性條件、順序限制、錯誤模式、必要的設定，以及效能特性。_避免使用_：API、signature（這兩者範圍太窄，只涉及型別層面的表面）。

**實作（Implementation）**：模組內部的東西，也就是它的程式碼本體。與 **Adapter（轉接器）** 不同：一個東西可以是小型轉接器搭配大型實作（例如 Postgres repo），也可以是大型轉接器搭配小型實作（例如記憶體內的假物件）。當話題聚焦於接縫時使用「adapter」；其餘情況則使用「implementation」。

**深度（Depth）**：介面所帶來的槓桿效益。呼叫方（或測試）每學會一單位的介面，就能運用多少行為。當大量行為藏在小巧的介面背後時，模組就是**深層的（deep）**；當介面幾乎和實作一樣複雜時，模組就是**淺層的（shallow）**。

**接縫（Seam）** _（Michael Feathers）_：一個可以在不修改該處程式碼的情況下改變行為的地方；也就是模組介面所在的*位置*。接縫該設在哪裡，是獨立於「接縫背後放什麼」的另一個設計決策。_避免使用_：boundary（與 DDD 的 bounded context 概念重疊）。

**轉接器（Adapter）**：在接縫上滿足介面的具體事物。描述的是*角色*（它填補了哪個位置），而非*內容*（裡面是什麼）。

**槓桿效益（Leverage）**：呼叫方從深度中獲得的好處。每學會一單位的介面，就能獲得更多能力。一份實作可以在 N 個呼叫點與 M 個測試中回收其成本。

**局部性（Locality）**：維護者從深度中獲得的好處。變更、錯誤、知識與驗證都集中在一處，而不是散落在各個呼叫方之間。修一次，處處都修好。

## 深層 vs 淺層

**深層模組（Deep module）** = 小介面 + 大量實作：

```
┌─────────────────────┐
│   Small Interface   │  ← 方法少，參數簡單
├─────────────────────┤
│                     │
│  Deep Implementation│  ← 複雜邏輯藏在裡面
│                     │
└─────────────────────┘
```

**淺層模組（Shallow module）** = 大介面 + 少量實作（應避免）：

```
┌─────────────────────────────────┐
│       Large Interface           │  ← 方法多，參數複雜
├─────────────────────────────────┤
│  Thin Implementation            │  ← 只是單純轉傳
└─────────────────────────────────┘
```

設計介面時，請自問：

- 能不能減少方法的數量？
- 能不能簡化參數？
- 能不能把更多複雜性藏在裡面？

## 原則

- **深度是介面的屬性，而非實作的屬性。** 深層模組內部可以由許多小巧、可 mock、可替換的部件組成；只是這些部件不屬於介面的一部分。一個模組可以同時擁有**內部接縫**（僅供其自身實作與測試使用）以及位於其介面上的**外部接縫**。
- **刪除測試法。** 想像把這個模組刪掉。如果複雜性因此消失，代表它只是個轉傳層。如果複雜性又在 N 個呼叫方那裡重新出現，代表它確實有其價值。
- **介面就是測試面。** 呼叫方與測試會經過同一個接縫。如果你想測試*超越*介面範圍的東西，這個模組的形狀大概就不對了。
- **一個轉接器代表假設性的接縫，兩個轉接器才代表真實的接縫。** 除非真的有東西會隨接縫而變化，否則不要引入接縫。

## 為可測試性而設計

好的介面能讓測試變得自然：

1. **接受依賴，而非自行建立依賴。**

   ```typescript
   // 可測試
   function processOrder(order, paymentGateway) {}

   // 難以測試
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **回傳結果，而非產生副作用。**

   ```typescript
   // 可測試
   function calculateDiscount(cart): Discount {}

   // 難以測試
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **小巧的表面積。** 方法愈少 = 需要的測試愈少。參數愈少 = 測試設置愈簡單。

## 關聯關係

- 一個**模組（Module）**只有一個**介面（Interface）**（呈現給呼叫方與測試的表面）。
- **深度（Depth）**是**模組**的屬性，是以其**介面**來衡量的。
- **接縫（Seam）**是**模組**的**介面**所在的位置。
- **轉接器（Adapter）**位在**接縫**上，並滿足該**介面**。
- **深度**為呼叫方帶來**槓桿效益**，為維護者帶來**局部性**。

## 被否決的框架方式

- **將深度定義為「實作行數／介面行數」的比值**（Ousterhout 提出）：這會鼓勵灌水實作內容。我們改用「深度即槓桿效益」的方式。
- **把「介面」等同於 TypeScript 的 `interface` 關鍵字或類別的 public 方法**：範圍太窄，此處所指的介面涵蓋呼叫方必須知道的每一項事實。
- **「Boundary」**：與 DDD 的 bounded context 概念重疊。請使用**接縫（seam）**或**介面（interface）**。
