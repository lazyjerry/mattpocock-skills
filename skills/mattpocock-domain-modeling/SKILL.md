# Domain Modeling（領域模型）

在設計過程中，主動建立並持續打磨專案的領域模型。這是一種*主動*的紀律：挑戰用語、發想邊界情境，並在術語表與決策一確立就立刻寫下來。（單純*閱讀* `CONTEXT.md` 來查詢用語並不算是這項技能，那只是任何技能都能做的一句話習慣。這項技能是用於你正在改動模型的時候，而不只是使用它。）

## 檔案結構

大多數 repo 只有單一個 context：

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

如果根目錄存在 `CONTEXT-MAP.md`，代表這個 repo 有多個 context。這份地圖會指出每一個 context 所在的位置：

```
/
├── CONTEXT-MAP.md
├── docs/
│   └── adr/                          ← 系統層級的決策
├── src/
│   ├── ordering/
│   │   ├── CONTEXT.md
│   │   └── docs/adr/                 ← context 專屬的決策
│   └── billing/
│       ├── CONTEXT.md
│       └── docs/adr/
```

檔案要按需建立：只在你有東西可寫的時候才建立。如果還沒有 `CONTEXT.md`，就在第一個術語確立時建立。如果還沒有 `docs/adr/`，就在需要第一份 ADR 時建立。

## 對話期間

### 對照術語表提出質疑

當使用者使用的術語與 `CONTEXT.md` 中既有的用語衝突時，要立刻指出來。「你的術語表把『取消』定義為 X，但你現在講的好像是 Y。到底是哪一個？」

### 釐清模糊的用語

當使用者使用模糊或涵義過廣的術語時，主動提出精確的標準用語。「你說的『帳戶』：你指的是 Customer 還是 User？這是兩個不同的東西。」

### 討論具體情境

當在討論領域關係時，用具體情境來做壓力測試。發想能夠探測邊界情況的情境，逼使用者對概念之間的界線講清楚。

### 與程式碼交叉比對

當使用者陳述某個東西是如何運作的，要檢查程式碼是否與之一致。如果發現矛盾，就指出來：「你的程式碼會取消整筆 Order，但你剛剛說可以部分取消。到底哪個才對？」

### 即時更新 CONTEXT.md

當某個術語確立後，就立刻在當下更新 `CONTEXT.md`。不要累積起來一次處理，要在發生的當下就記錄下來。格式請參考 [CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md)。

`CONTEXT.md` 應該完全不包含實作細節。不要把 `CONTEXT.md` 當成規格書、草稿紙，或實作決策的存放處。它只是一份術語表，僅此而已。

### 謹慎地提議撰寫 ADR

只有在以下三個條件同時成立時，才提議建立 ADR：

1. **難以逆轉**：日後改變主意的代價相當可觀
2. **沒有背景脈絡會令人意外**：未來的讀者會想「他們當初為什麼要這樣做？」
3. **確實經過權衡取捨**：存在真正的替代方案，而你基於具體理由選擇了其中一個

只要三者缺一，就不要寫 ADR。格式請參考 [ADR-FORMAT.md](./ADR-FORMAT.md)。
