# ADR 格式

ADR 存放在 `docs/adr/` 目錄中，並使用連續編號：`0001-slug.md`、`0002-slug.md`，依此類推。

只有在需要建立第一份 ADR 時，才建立 `docs/adr/` 目錄。

## 範本

```md
# {決策的簡短標題}

{1 到 3 句話：背景是什麼、做出了什麼決定、以及原因。}
```

就這樣。一份 ADR 可以只是一個段落。它的價值在於記錄「做出了某個決定」以及「為什麼」，而不是把每個段落都填滿。

## 選擇性章節

只有在確實能帶來實質價值時才加入這些章節。大多數 ADR 都不需要。

- **Status** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）：當決策可能會被重新檢視時很有用
- **Considered Options**：只有在被否決的替代方案值得記錄時才加入
- **Consequences**：只有在需要指出非顯而易見的後續影響時才加入

## 編號規則

掃描 `docs/adr/` 目錄，找出目前最大的編號並加一。

## 何時該建議寫一份 ADR

以下三項都必須成立：

1. **難以逆轉**：日後改變主意的代價相當可觀
2. **沒有背景脈絡會令人意外**：未來的讀者看到這段程式碼時，會納悶「當初到底為什麼要這樣做？」
3. **確實經過權衡取捨**：當時存在真正的替代方案，而你基於具體理由選了其中一個

如果決策很容易逆轉，就跳過：反正之後可以直接改回來。如果它不會讓人意外，就不會有人納悶為什麼。如果當時根本沒有真正的替代方案，除了「我們做了顯而易見的事」之外，也沒什麼好記錄的。

### 什麼樣的決策符合條件

- **架構形態。**「我們採用單一儲存庫（monorepo）。」「寫入模型採用事件溯源（event-sourced），讀取模型則投影（projected）到 Postgres。」
- **情境（context）之間的整合模式。**「Ordering 與 Billing 是透過領域事件（domain events）溝通，而不是同步 HTTP。」
- **會帶來鎖定效應（lock-in）的技術選擇。** 資料庫、訊息匯流排（message bus）、驗證供應商、部署目標。不是每個函式庫都要記錄：只記錄那些要花上一季時間才能換掉的。
- **邊界與範圍的決策。**「客戶資料由 Customer 情境擁有；其他情境只能透過 ID 參照它。」明確說「不」的決策，和說「是」的決策一樣有價值。
- **刻意偏離顯而易見做法的決策。**「我們用手寫 SQL 而不是 ORM，因為 X。」任何一個理性的讀者會預期你選了相反做法的情況。這能避免下一位工程師「修正」一個其實是刻意為之的設計。
- **程式碼中看不出來的限制條件。**「我們不能用 AWS，因為法規遵循（compliance）的要求。」「回應時間必須在 200ms 以內，因為合作夥伴 API 合約的規定。」
- **當否決理由不明顯時，記錄被否決的替代方案。** 如果你曾考慮過 GraphQL 但基於一些細微理由選擇了 REST，就把它記錄下來；否則六個月後又會有人重新提議用 GraphQL。
