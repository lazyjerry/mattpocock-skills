你已取得一份規格。這份規格應該有相關的工單（tickets），描述如何實作該規格。

目標是產出一個 PR，在單一分支上實作整份規格。

這些工單並不是一份步驟清單，而是一個**任務圖**（task graph），彼此之間存在阻塞關係。這代表隨時都會有一批**前緣**（frontier）工單處於可以立即進行的狀態。

與子代理（subagent）之間的溝通應該力求精簡。主要透過**情境指標**（context pointers）來溝通：指向規格、工單、研究筆記與先前的提交（commit）。不要重複已經可以透過指標取得的資訊。

**實作子代理**應盡可能在背景執行，以達到**最大並行度**。

## 步驟

1. 閱讀規格與工單，充分理解任務圖。

2. （選用）使用一個**探索子代理**來進行工單所需的探索工作，例如相關的程式碼庫檔案或外部文件。務必確保探索子代理可以儲存檔案，它應將其 Markdown 筆記儲存在儲存庫（repo）之外、所有後續子代理都能存取的目錄中。這樣可以讓**實作子代理**專注於實作本身，而非探索工作。

3. 建立一個分支，並開一個草稿（draft）PR。此 PR 應標記為「關閉」（closing）該規格議題（issue）與相關工單。

4. 使用**實作子代理**來實作每一張工單。每個實作子代理都應在自己的工作樹（worktree）中作業，並使用自己的分支。

5. 一旦某個**實作子代理**完成工作，便用一個**合併子代理**（merger subagent）將其成果合併回 PR 分支。

6. 如果這改變了可用工單的**前緣**，就啟動更多**實作子代理**來處理新的工單。這樣可以維持最大並行度。

7. 所有工單都完成後，在 PR 分支上執行 /code-review。將程式碼審查提出的所有問題，交由單一**實作子代理**統一修正。

8. 將該 PR 標記為可供審查（ready for review）。

9. 清理所有**實作子代理**的工作樹（worktree）。
